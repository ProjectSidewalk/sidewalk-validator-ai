# Code audit, 14 October 2026

The first review of this repository by anyone other than its author. It was done read-only against
`master` at `eb9bc65`, with every claim below checked against a live service (the v3 API, Google's
tile endpoint, Hugging Face) or against the published artifacts, and it is the source for the
issues it links. The README summarises the state of the pipeline; this document holds the evidence.

What was read: all four scripts and three SLURM files; the vendored `Depth-Anything-V2/` tree
(diffed against upstream `a561b84`); the five published models' `trainer_state.json`,
`config.json` and `preprocessor_config.json`; the five published datasets' file listings; the
serving code in [sidewalk-ai-api](https://github.com/ProjectSidewalk/sidewalk-ai-api)
(`main.py`, `validator.py`, `depthanything.py`, `panorama.py`); the orchestration in
[SidewalkWebpage](https://github.com/ProjectSidewalk/SidewalkWebpage) (`AiService.scala`,
`LabelTable.scala`, `LabelApiController.scala`, `docs/ai-subsystems.md`); and the two predecessor
papers, [Weld et al. 2019](https://doi.org/10.1145/3308561.3353798) and
[Duan et al. 2022](https://doi.org/10.1145/3517428.3550381).

What was measured: one city's full `rawLabels` export (Teaneck, NJ, 23,395 labels), one tile
request with and without browser headers, and the `/v3/api/overallStats` endpoint of all 41 public
deployments. Commands to reproduce each number are at the end.

Fixed in the accompanying PR: findings 1, 2, 3 (the training-signal part), 9 (the out-of-frame
check), 10 (a guard that refuses to run when the class folders are missing; empty folders still pass,
which PR #25's manifest-based split removes), 11 and 12 (the filters). Everything else is an issue.

## Findings, ranked

### 1. The v3 API renamed the panorama column; the script raises `KeyError` on the first label

`data_generation.py` read `row['gsv_panorama_id']`. The v3 `rawLabels` CSV calls the column
`pano_id` (`LabelApiModels.scala:323-370` in SidewalkWebpage; confirmed on the live Teaneck export).
There is no `gsv_panorama_id` anywhere in the v3 code, so the pipeline has not been runnable since the
v3 column names settled. **Fixed in the PR.**

### 2. Google's tile endpoint now returns 403 without browser headers; every panorama would fail

The tile fetcher sent bare `requests.get(url)`. Measured 2026-10-14 for pano `DsCvWstZYz9JL81V9NloOQ`
(tile x=5, y=2, zoom=4):

| headers | status | body |
|---|---|---|
| none | 403 | 126-byte JSON (`PERMISSION_DENIED`) |
| `User-Agent` + `Referer` (as in sidewalk-ai-api) | 200 | 45 KB JPEG |

The fetcher catches the failure, so a run would log "Could not fetch panorama" for every label and
finish with an empty dataset and exit code 0. The serving code added the headers on 2026-06-05 (sidewalk-ai-api
[`94ee55a`](https://github.com/ProjectSidewalk/sidewalk-ai-api/commit/94ee55a));
the auto-labeler switched to `streetlevel` for the same reason
(`sidewalk-auto-labeler/docs/design-review-2026-07.md` §3.7). **Fixed in the PR** (headers added;
reading from the pano store instead is [#8](https://github.com/ProjectSidewalk/sidewalk-validator-ai/issues/8)).

### 3. The training signal includes the deployed validator's own votes

Since AI validation shipped ([SidewalkWebpage#3978](https://github.com/ProjectSidewalk/SidewalkWebpage/pull/3978), merged 2025-08-01), the `SidewalkAI` account's
votes are counted in `label.agree_count` / `disagree_count` like any other user's
(`FilteredTables.isVerdictVote`, `FilteredTables.scala:150-166`, excludes only the label's author,
stale-type votes and admin-excluded users; the AI user is not excluded). `data_generation.py` built
its classes from those two columns.

Teaneck, live export, CurbRamp + all types, applying the script's own thresholds:

| counting | `correct` (net ≥ 3 agree) | `incorrect` (net ≥ 2 disagree) |
|---|---|---|
| API columns (AI votes included) | 6,981 | 573 |
| human votes only | 3,969 | 417 |

As sets, 44% of the labels in the API-count `correct` set and 31% of the API-count `incorrect` set are
not in the corresponding human-only set. A retrain from the API columns learns the current model's
output.

Are the deployed models clean? Each Hugging Face model repo holds two uploads, 2025-01-26 and
2025-08-16, with different weights and trainer runs. sidewalk-ai-api's `model_map.py` pins the
**2025-08-16** revisions, and every metric in this document comes from those August runs. They were
trained around 2025-08-14. AI validation merged in [SidewalkWebpage#3978](https://github.com/ProjectSidewalk/SidewalkWebpage/pull/3978) on
2025-08-01, the earliest `label_ai_assessment` row is from 2025-08-13, and the nightly
`GetAiValidationsActor` sweep was added on 2025-09-17
([`7b6e9d720b`](https://github.com/ProjectSidewalk/SidewalkWebpage/commit/7b6e9d720b)). The models were therefore trained before the nightly sweep,
so "clean" most likely holds, but AI votes cast between 2025-08-01 and the data pull are not ruled out. The `validations` column carries a `validator_type` per
vote, which is what the PR now counts. **Fixed in the PR**; PR #25 makes the rule fail closed
(`validator_type == "Human"`).

### 4. The split leaks across panoramas

`split_data.py` shuffles files, not panoramas. In Teaneck, labels of all types average **2.78 per
panorama** and **5,413 of 8,415 panoramas (64%)** carry more than one label. Within one type's selected
set the clustering is weaker but real: CurbRamp 1.66 labels per panorama (62% of its labels share a
panorama), SurfaceProblem 1.19 (27%), Obstacle 1.00. Two curb ramps on one corner give two
overlapping crops that can land in `train` and `test`. Weld et al. 2019 partitioned panoramas 80/10/10
to avoid exactly this. Every published metric, including the confidence map that becomes
`validation_estimated_accuracy`, is optimistic by an unknown amount. Neither shuffle was seeded.
[#3](https://github.com/ProjectSidewalk/sidewalk-validator-ai/issues/3); seeds added in the PR.

### 5. The confidence-to-precision map is computed under the wrong prior

`data_generation.py` forces 55:45 correct:incorrect (`CORRECT_PROPORTION`). `get_stats.py` sweeps
confidence over the test split and records, per class, the precision among predictions above each
threshold. `sidewalk-ai-api/main.py` serves that as `validation_estimated_accuracy`, and
`AiService.scala:184-187` casts a real vote only when it is ≥ `ai-validation-min-accuracy` (0.92 in
every city). Production traffic is not 55:45: on human votes alone Teaneck has 3,969 correct vs 417
incorrect labels (≈ 90:10). That is the balance among labels the crowd decided, a proxy for production
traffic rather than a measurement of it, but either way it is far from 55:45. Precision depends on the class prior, so the served number overstates
the accuracy of "incorrect" verdicts and understates "correct" ones.

The platform's own statistics confirm it. `/v3/api/overallStats` from all 41 public deployments,
labels where the AI voted (i.e. cleared the gate) and a human majority exists (AI excluded):

| AI verdict | human majority agrees | admin majority agrees |
|---|---|---|
| correct (n = 231,956) | 96.0% | 97.9% |
| incorrect (n = 37,715) | 57.2% | 61.6% |

(Live `overallStats` as of 2026-10-14; the figures drift by a few tenths of a point day to day.)

Overall agreement 90.5% with the human majority (κ = 0.57) and 92.5% with Owner/Administrator
majorities (κ = 0.67). [#4](https://github.com/ProjectSidewalk/sidewalk-validator-ai/issues/4).

### 6. Training and evaluation/serving preprocess images differently

`fine_tune_classifier.py:41-45`: `RandomResizedCrop(256)` + `ToTensor()`, with `Normalize`
commented out, applied through `dataset.with_transform` to the validation split as well.
`get_stats.py:66` and `sidewalk-ai-api/validator.py:15`: the checkpoint's `AutoImageProcessor`
(`preprocessor_config.json`: resize shortest edge 256, center-crop 224, rescale, `do_normalize: true`
with ImageNet mean/std). Checkpoints were selected under the first pipeline and are deployed under
the second. [#5](https://github.com/ProjectSidewalk/sidewalk-validator-ai/issues/5).

### 7. Training and serving build different crops

| | training (`data_generation.py`) | serving (`sidewalk-ai-api/main.py`) |
|---|---|---|
| camera | yaw to label, **pitch 0**; label off-centre | yaw **and pitch** to label; label centred |
| depth model | `depth_anything_v2_metric_vkitti_vitl` | `DepthAnythingPredictor(encoder='vitb')` |
| crop rule | `crop_half = 6100 / depth` on a 2048² 90° view | same |

Same formula, different inputs. [#5](https://github.com/ProjectSidewalk/sidewalk-validator-ai/issues/5),
[sidewalk-ai-api#8](https://github.com/ProjectSidewalk/sidewalk-ai-api/issues/8).

### 8. `get_stats.py` reports recall-at-precision from an unsorted array

`np.searchsorted(precision, level)` (`get_stats.py:145`, `:257`) assumes `precision` is sorted;
`sklearn.metrics.precision_recall_curve` does not return a sorted array. The numbers printed into
`report.png` are therefore not the recall at that precision. The last loop can also index
`thresholds` (length n−1) with an index valid for `precision` (length n).
[#6](https://github.com/ProjectSidewalk/sidewalk-validator-ai/issues/6); PR
[#22](https://github.com/ProjectSidewalk/sidewalk-validator-ai/pull/22) (closed unmerged) proposed a fix.

### 9. Labels outside the perspective frame are not checked

`equirectangular_point_to_perspective` returns pixel coordinates without checking them against the
2048² frame (pitch 0, so it spans ±45° of elevation). A label below −45° (y/h > 0.75; 0.6% of Teaneck
labels, 1st–99th percentile of y/h 0.52–0.73) gets a row past the end of the depth map, so
`depth[center_y, center_x]` raised `IndexError` and the label was skipped as a generic error, never
silently misread. A silent read of the opposite edge needs a negative row, i.e. a label above +45°
(y/h < 0.25), and none exist in 1,071,562 cached rows. (Issue #9 says "below +45°" where it means
below −45°.) **Explicit check added in the PR**; the rest of
[#9](https://github.com/ProjectSidewalk/sidewalk-validator-ai/issues/9) remains.

### 10. A second run of `split_data.py` deletes the dataset

It removes `ds/` first, then copies from `correct/` and `incorrect/`, then deletes those. Run twice,
the second run finds nothing to copy after having removed `ds/`. **Guard added in the PR**;
[#10](https://github.com/ProjectSidewalk/sidewalk-validator-ai/issues/10) makes it idempotent.

### 11. The Chicago CSV hot-fix is dead code

The `.replace("Little Italy, UIC", "")` workaround references
[SidewalkWebpage#3756](https://github.com/ProjectSidewalk/SidewalkWebpage/issues/3756), closed
2025-04-02. **Removed in the PR.**

### 12. No provider, coordinate or authorship filters

Labels from Mapillary/Panoramax panoramas (`pano_source`) were sent to the Google tile endpoint;
legacy labels with unconverted coordinates (negative `pano_y`: Seattle 193, CDMX 14, Pittsburgh 8,
SPGG 1; SidewalkWebpage `docs/data-notes.md`) were not excluded;
RampNet-placed labels (user `51b0b927-…`) are included although production never validates them.
**GSV and `pano_y ≥ 0` filters added in the PR**; the authorship decision is in
[#9](https://github.com/ProjectSidewalk/sidewalk-validator-ai/issues/9).

### 13. The published CurbRamp dataset is a copy of the Crosswalk dataset

`projectsidewalk/sidewalk-validator-ai-dataset-curbramp` and `…-crosswalk` list the same 1,585
image files (train 597/511, val 128/109, test 129/111); `test/correct/chicago_10689.webp` has MD5
`0858796afd397461800713a9124d6055` in both and shows a crosswalk. The curbramp model's
`trainer_state.json` records 103 optimizer steps per epoch at an effective batch of 32, i.e. about
3,300 training images, so the real dataset was never uploaded (the two uploads are three minutes
apart on 2025-08-16). [#7](https://github.com/ProjectSidewalk/sidewalk-validator-ai/issues/7).

### 14. Model repos ship training residue

Each model repo carries `optimizer.pt` (2,435 MB), `scheduler.pt`, `rng_state.pth` and
`training_args.bin` beside the 1,218 MB `model.safetensors`. The API's `download_hf_models.py` now
fetches only what it needs (`allow_patterns`), but any other consumer of the repos downloads it all. No model
or dataset cards ([#2](https://github.com/ProjectSidewalk/sidewalk-validator-ai/issues/2)).
[#7](https://github.com/ProjectSidewalk/sidewalk-validator-ai/issues/7).

### 15. Hygiene

No LICENSE, tests, CI or seeds. `Depth-Anything-V2/` is vendored at 64 MB (demo videos, a 12 MB
teaser, 87k-line split lists, committed `.pyc`), byte-identical to upstream except one
`requirements.txt` pin; the API uses a submodule. `environment.yml` embeds
`prefix: /gscratch/scrubbed/jsomeara/...` and 150 pins including dash, flask, jupyter and open3d.
Nineteen city hostnames are hardcoded (59 deployments exist, 41 public and 18 private;
`/v3/api/cities` lists them; keelung, new-taipei and taipei are among the private ones). Each of the
five label-type processes downloaded all nineteen CSVs. The tile pool was sized at 1,000 threads, but
a zoom-4 panorama is 128 tiles, a handful of which are fetched during the dimension probe, so fewer than 128 threads ever ran, at 1,000
or at the 100 the PR sets; the change is harmless tidying, not a rate-limit fix.
[#8](https://github.com/ProjectSidewalk/sidewalk-validator-ai/issues/8),
[#11](https://github.com/ProjectSidewalk/sidewalk-validator-ai/issues/11).

## What is right

- The vendored depth code is unmodified upstream (`diff -rq` against `a561b84`: only
  `requirements.txt` differs).
- Sampled crops from the published datasets are well centred on the labelled feature and the
  depth-scaled sizing behaves as intended: near objects get tight crops, far ones wide crops.
- The training configuration is sensible for full fine-tuning of ViT-L (lr 1e-5, effective batch 32,
  warm-up 10%, 25 epochs) and checkpoint selection by validation macro-F1 is the right criterion.
- The label-selection thresholds (net ≥ 3 agree, net ≥ 2 disagree) are asymmetric in the right
  direction given how much rarer disagree votes are.

## Reproducing the measurements

```bash
# Column names, AI votes, labels per panorama, y-position quantiles (one city; ~16 MB)
curl -s "https://sidewalk-teaneck.cs.washington.edu/v3/api/rawLabels?filetype=csv" -o teaneck.csv
python3 - <<'EOF'
import csv, json, collections
rows = list(csv.DictReader(open("teaneck.csv")))
print(list(rows[0].keys())[:5])                      # label_id, user_id, pano_id, ...
def cls(a, d): return "incorrect" if d - a > 1 else "correct" if a - d > 2 else None
api, human = collections.Counter(), collections.Counter()
for r in rows:
    v = json.loads(r["validations"] or "[]")
    ah = sum(x["validation"] == "Agree" for x in v if x["validator_type"] != "AI")
    dh = sum(x["validation"] == "Disagree" for x in v if x["validator_type"] != "AI")
    api[cls(int(r["agree_count"]), int(r["disagree_count"]))] += 1; human[cls(ah, dh)] += 1
print(api, human)
pc = collections.Counter(r["pano_id"] for r in rows)
print(len(rows) / len(pc), sum(c > 1 for c in pc.values()), len(pc))
EOF

# Tile endpoint with and without headers
P=DsCvWstZYz9JL81V9NloOQ; U="https://streetviewpixels-pa.googleapis.com/v1/tile?cb_client=maps_sv.tactile&panoid=$P&x=5&y=2&zoom=4"
curl -s -o /dev/null -w "%{http_code}\n" "$U"
curl -s -o /dev/null -w "%{http_code}\n" -H "User-Agent: Mozilla/5.0" -H "Referer: https://www.google.com/maps" "$U"

# Dataset duplication
for d in crosswalk curbramp; do curl -s "https://huggingface.co/api/datasets/projectsidewalk/sidewalk-validator-ai-dataset-$d" \
  | python3 -c 'import sys,json; print("\n".join(sorted(s["rfilename"] for s in json.load(sys.stdin)["siblings"])))' > $d.txt; done
cmp crosswalk.txt curbramp.txt && echo identical

# Platform-wide AI vs human/admin majority: /v3/api/overallStats -> ai_stats, for every url in /v3/api/cities
```
